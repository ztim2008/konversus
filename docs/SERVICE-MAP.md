# SERVICE MAP

Карта отдельных сервисов и подпроектов вокруг AVITO CONVERSION BUILDER.

## Зачем нужен этот документ

Этот файл фиксирует важную вещь: папки вроде `avitoeditor`, `avitologi`, `html-enhancer` и `portfolio` не считаются мусором или случайным legacy.

Для этого проекта они рассматриваются как отдельные сервисные подпроекты, которые могут:
- жить рядом с core-платформой;
- давать отдельную ценность пользователю;
- интегрироваться в основной продукт как модули, инструменты или витрины;
- развиваться отдельно от core API.

Сейчас они временно не входят в публичный GitHub mirror только по одной причине: сначала нужна санация секретов, backup-артефактов и слабых мест безопасности.

## Главный принцип

Core-платформа и сервисные подпроекты не конфликтуют.

Целевая модель такая:
- `api/core` и `cabinet` — ядро основной платформы AVITO CONVERSION BUILDER;
- отдельные подпроекты — самостоятельные сервисы или продуктовые спутники;
- со временем часть из них может быть встроена в единый кабинет, single sign-on, общую аналитику или общий биллинг.

## Карта сервисов

| Папка | Статус | Роль | Как связана с core-платформой | Что важно сейчас |
|---|---|---|---|---|
| `avitoeditor` | Отдельный сервис | Визуальный редактор карточек и креативов для Avito | Может стать модулем визуального улучшения внутри audit/improvement workflow | Не удалять, не ломать, сначала санировать secrets/backups/admin-доступ |
| `avitologi` | Отдельный сервис | Каталог/биржа специалистов по Авито | Может стать acquisition-слоем, каталогом исполнителей или партнерским модулем | Не удалять, сначала убрать client-side admin-пароль и привести к безопасной публикации |
| `html-enhancer` | Отдельный сервис | Визуальный редактор/мини-CMS для HTML-сайтов | Может использоваться как внутренний редактор лендингов, help-страниц и промо-контента | Не удалять, сначала убрать дефолтный fallback-пароль и пройти санацию |
| `portfolio` | Отдельный сервис | Портфолио-витрина, медиа и кейсы | Может стать публичной proof/portfolio-зоной для роста доверия и продаж | Не удалять, сначала пройти отдельный security-аудит перед публикацией |
| `avito-portfolio-production` | Отдельный контур/артефакт | Production-сборка или отдельная версия portfolio-направления | Может быть полезен как reference или deploy-слой, но не как основной source of truth | Не трогать без отдельной задачи; сначала понять, нужен ли перенос в нормальный сервисный контур |
| `_backups` | Служебный архивный контур | Бэкапы и исторические артефакты | Не является сервисом продукта, но важен для rollback и истории | Не публиковать в GitHub и не удалять без осознанного backup-решения |

## Как это выглядит на уровне продукта

Текущая архитектурная логика:
- основное ядро продукта строится вокруг подключения аккаунта, аудита объявлений и роста конверсии;
- сервисные подпроекты усиливают ядро не как хаотичные папки, а как будущие специализированные модули;
- часть из них может остаться независимой, часть со временем может быть включена в единый продуктовый контур.

Примеры:
- `avitoeditor` → модуль создания улучшенной версии изображения или инфографики после аудита;
- `avitologi` → канал привлечения исполнителей, партнеров или marketplace-слой;
- `html-enhancer` → инструмент редактирования маркетинговых и help-страниц проекта;
- `portfolio` → публичная витрина кейсов и доказательств ценности.

## Почему они сейчас исключены из публичного mirror

Это не удаление и не отказ от подпроектов.

Текущий статус означает только одно:
- сначала безопасность и санитария;
- потом публикация в GitHub второй волной;
- до этого момента папки продолжают жить на сервере и сохраняются как активы проекта.

Подробности и найденные блокеры описаны в `docs/LEGACY-SANITIZATION.md`.

## Правило работы с этими папками

1. Не менять подпроекты без явной задачи.
2. Не публиковать их автоматически в публичный репозиторий без санации.
3. Рассматривать каждую папку как отдельный сервисный контур со своим жизненным циклом.
4. Перед интеграцией в core-платформу сначала фиксировать продуктовую роль и сценарий использования.
5. Если подпроект нужен для Core MVP, интеграция должна идти отдельной задачей с понятным API или UX-контрактом.

- описать минимальный сценарий, как он подключается к основной платформе;
- после этого добавлять его в GitHub как отдельный сервисный подпроект.
