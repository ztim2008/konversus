# GIT WORKFLOW

Простой взрослый git-процесс для этого проекта.

## 1. Главный принцип

`main` — только для стабильного состояния.

Если изменение рискованное, заметное по объему или затрагивает backend, auth, SQL, интеграции, деплой или процессы, работа идет в отдельной ветке.

## 2. Какие ветки используем

- `main` — текущее стабильное состояние проекта.
- `feature/*` — новая пользовательская или продуктовая функциональность.
- `fix/*` — исправления багов.
- `docs/*` — изменения документации и процессов.
- `process/*` — git, deploy, staging, workflow и операционные изменения.

Примеры:
- `feature/avito-oauth-start`
- `fix/audit-endpoint-auth-error`
- `docs/mvp-map-update`
- `process/legacy-sanitization`

## 3. Когда нельзя работать прямо в main

Нельзя работать прямо в `main`, если задача затрагивает:
- API;
- SQL и миграции;
- OAuth и токены;
- кабинет и auth flow;
- деплой, релиз и инфраструктурный контур;
- рискованные изменения в legacy-папках.

Прямой коммит в `main` допустим только для совсем маленьких и безопасных правок, например:
- опечатка в документации;
- небольшой текст на лендинге;
- правка ссылки или неопасного статического блока.

Даже для таких задач отдельная ветка все равно предпочтительнее.

## 4. Минимальный цикл работы

1. Создать ветку от `main`.
2. Сделать изменение.
3. Проверить сценарий.
4. Обновить docs и CHANGELOG.md.
5. Сделать commit.
6. Пушить ветку в GitHub.
7. После проверки объединять в `main`.

## 5. Правило коммитов

Коммит должен быть коротким и предметным.

Нормально:
- `add deployment strategy and staging plan`
- `sanitize avitoeditor env example`
- `wire audit screen to backend endpoint`

Плохо:
- `fix`
- `updates`
- `many changes`

## 6. Правило merge

Перед merge в `main` нужно:
1. Убедиться, что затронутый сценарий проверен.
2. Убедиться, что docs и CHANGELOG.md обновлены.
3. Убедиться, что в diff нет env, backup, архивов и секретов.
4. Если менялись backend, SQL или auth — свериться с RELEASE-CHECKLIST и RUNBOOK.

## 7. Текущий рабочий стандарт

С этого момента проект ведем так:
- `main` держим чистым и стабильным;
- все рискованные изменения делаем в отдельных ветках;
- legacy-санацию и staging-подготовку делаем только отдельными ветками;
- GitHub считаем обязательной частью рабочего контура.
