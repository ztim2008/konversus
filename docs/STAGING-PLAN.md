# STAGING PLAN

План перехода от production-like разработки к отдельному staging-контуру.

## 1. Зачем нужен staging

Сейчас backend и часть продуктовых изменений делаются прямо в рабочем окружении домена.

Это дает скорость, но создает риски:
- можно сломать auth или API прямо на рабочем домене;
- миграции и интеграции проверяются слишком поздно;
- production становится одновременно dev-средой и боевым контуром.

Staging нужен, чтобы risky-изменения сначала проходили отдельный проверочный контур.

## 2. Что должен включать staging минимум

Минимальный staging-контур:
- отдельный поддомен, например `staging.xn--80abnjzcaex7a.xn--p1ai`;
- отдельный каталог проекта;
- отдельный env-файл;
- отдельная база данных или отдельная схема с тестовыми данными;
- отдельные OAuth redirect URI для Яндекс и Avito, если требуется;
- health endpoint и базовая smoke-проверка.

## 3. Какие задачи сначала уводим в staging

В staging первыми должны идти:
- Avito OAuth flow;
- импорт объявлений;
- SQL-миграции;
- audit backend;
- benchmark ingestion;
- auth и refresh token lifecycle.

## 4. Что можно пока оставлять без staging

Без staging пока можно делать только:
- документацию;
- контентные правки;
- неопасные визуальные изменения лендинга;
- статические страницы без backend-эффекта.

## 5. Пошаговый план внедрения

### Phase 1. Организация

Нужно подготовить:
1. отдельную директорию для staging;
2. отдельный env;
3. отдельную базу или схему;
4. отдельный список доменных URL и callback URL.

### Phase 2. Git и выкат

Нужно закрепить правило:
1. feature/fix/process ветка;
2. выкладка в staging;
3. проверка сценария;
4. merge в `main`;
5. выкладка в production.

### Phase 3. Проверки

Минимальный checklist staging:
1. health endpoint отвечает;
2. auth работает;
3. кабинет открывается;
4. API не падает на основном сценарии;
5. миграции проходят без ручного хаоса.

## 6. Когда считать staging внедренным

Staging считается реально внедренным, когда:
- есть отдельный URL;
- есть отдельный env;
- есть отдельная БД или схема;
- хотя бы один risky backend flow уже проверяется там до production.

## 7. Следующий практический шаг

Первый реальный шаг сейчас:
- выделить staging-поддомен и staging-env для core-платформы,
- не трогая пока legacy-подпроекты.
