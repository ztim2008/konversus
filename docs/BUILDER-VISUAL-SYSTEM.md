# Визуальная система builder shell

## Зачем нужен этот документ

Этот документ фиксирует визуальный baseline для builder shell.

Он нужен, чтобы редактор концепта дальше развивался как производственный workspace, а не откатывался в мягкую SaaS-эстетику с большими скруглениями и воздухом ради воздуха.

## Визуальный принцип

Builder для производственного B2B должен выглядеть как рабочая среда:

- плотная,
- собранная,
- структурная,
- инженерная по ритму,
- без декоративной округлости.

Главный ориентир: не glassmorphism и не lifestyle dashboard, а цифровой пульт сборки коммерческого документа.

## Базовый характер интерфейса

В интерфейсе builder shell принимаются такие правила:

1. Большие панели, карточки, формы и кнопки работают без выраженных скруглений.
2. Иерархия строится через линии, контраст поверхностей, вертикальные акценты и плотность сетки.
3. Ритм держится на повторяемых шагах по 4, 8, 12, 16 и 24 px.
4. Основной визуальный язык задают бордеры, моноширинные кикеры, инженерная типографика и спокойный индустриальный фон.
5. Акцент должен чувствоваться как сигнал управления, а не как декоративная подсветка.

## Палитра

### Базовые тона

- фон workspace: почти черный с холодным стальным уклоном,
- основная поверхность: темный графит,
- усиленная поверхность: более тяжелый графит с теплым верхним свечением,
- поле ввода: глубокий темный металл,
- линии: холодные светлые линии с низкой непрозрачностью.

### Акценты

- основной сигнал: теплый янтарный,
- вспомогательный холодный сигнал: стальной голубой только как слабая примесь,
- danger-состояние: приглушенный красный без кислотности.

### Практическое правило

Теплый акцент нужен для действия и фокуса.
Холодный тон нужен для среды и глубины.
Смешивать их равноправно нельзя: янтарь должен управлять вниманием, а не конкурировать с фоном.

## Токены

В scoped builder layer должны существовать отдельные токены:

- `--builder-bg`
- `--builder-surface`
- `--builder-surface-alt`
- `--builder-surface-strong`
- `--builder-line`
- `--builder-line-strong`
- `--builder-text`
- `--builder-muted`
- `--builder-muted-strong`
- `--builder-accent`
- `--builder-accent-strong`
- `--builder-danger`

Их задача не только хранить цвета, но и удерживать характер оболочки:

- поверхность должна быть тяжелой,
- линия должна быть читаемой,
- акцент должен быть редким и дисциплинированным.

## Типографика

### Роли

- заголовки панелей: плотные, крупные, без излишнего воздуха,
- основной текст: нейтральный, читабельный, не слишком светлый,
- кикеры и служебные ярлыки: моноширинные, верхний регистр, большой tracking,
- кнопки и chip-элементы: компактные, верхний регистр, ощущение управляющей панели.

### Практическое правило

Типографика должна создавать ощущение production board:

- смысловые блоки читаются быстро,
- служебные подписи не спорят с контентом,
- заголовки не выглядят рекламными.

## Сетка и плотность

### Layout shell

Builder использует трехпанельную схему:

- слева узкий rail навигации и каталога,
- в центре основной документ,
- справа плотная колонка публикации и контекстных состояний.

### Плотность

Нужно соблюдать такие правила:

- минимизировать пустые декоративные поля,
- держать короткие расстояния между связанными элементами,
- не превращать catalog cards в большие плитки,
- не делать формы визуально мягче, чем панели вокруг них.

## Состояния

### Базовые состояния shell

- обычная панель,
- усиленная панель,
- compact card,
- insertion zone,
- success note,
- error note,
- active state,
- disabled/passive state.

### Как они должны различаться

- активность показывается не только цветом, но и конструктивным акцентом по границе,
- success и error состояния не должны выбиваться по форме, только по тону и сигналу,
- insertion zone должна выглядеть как рабочая точка монтажа, а не как пустой placeholder,
- compact cards должны держать ритм списка и быстро сканироваться глазами.

## Карточки

### Навигационные карточки

Навигационная карточка должна:

- занимать минимум высоты,
- быстро показывать категорию и название,
- поддерживать статус видимости,
- иметь четкое active-state отличие.

### Карточки каталога

Карточки каталога должны:

- быть компактнее document cards,
- иметь жесткую геометрию,
- использовать вертикальный акцент, а не rounded-плашку,
- держать короткое описание и явный action.

### Карточки предпросмотра

Карточки предпросмотра должны:

- восприниматься как выжимка клиентской страницы,
- быть собранными и сухими,
- держать заголовок, текст и списки без визуального мусора.

## Блоки каталога

Каталог block library строится по следующим правилам:

1. Категория сначала читается как системный раздел.
2. Внутри раздела блоки идут плотным стеком.
3. Кнопка добавления не должна быть больше самого содержания карточки.
4. Описание блока должно быть коротким, прикладным и без маркетинговой воды.
5. Каталог должен ощущаться как библиотека модулей, а не как витрина.

## Формы

Поля ввода, select и textarea в builder shell должны:

- быть прямыми по геометрии,
- иметь одинаковый контур,
- использовать темную металлическую подложку,
- показывать focus через линию и акцентный edge, а не через мягкое свечение.

## Что запрещено

В builder shell не должно появляться:

- больших rounded-pill кнопок как базового паттерна,
- стеклянных blur-панелей как главного визуального языка,
- рыхлых карточек с большим пустым воздухом,
- ярких gradient-блоков ради декоративности,
- мягкой consumer SaaS-эстетики.

## Практическое следствие для дальнейшей разработки

Любой новый элемент в builder сначала проверяется вопросом:

`это похоже на производственный рабочий пульт или снова скатывается в мягкую админку?`

Если ответ неочевиден, элемент нужно упростить, уплотнить и убрать лишнюю округлость.
