# UX-схема Proposal Builder

## Зачем нужен этот документ

Этот документ фиксирует exact UX-схему proposal builder как product interaction system.

Он описывает не только layout, но и роль каждой зоны интерфейса:

- левый sidebar,
- canvas,
- right panel,
- механики вставки блоков,
- продуктовую логику работы builder.

## Продуктовый принцип

Builder должен ощущаться не как CRUD-редактор и не как CMS, а как workspace для сборки B2B digital pitch.

Поэтому интерфейс строится по логике presentation workflow:

1. слева пользователь выбирает и понимает narrative-структуру,
2. в центре он собирает и редактирует документ,
3. справа он видит delivery-слой, preview-логику и режим публикации.

## Layout builder-а

Базовая схема:

- левый sidebar,
- центральный canvas,
- right panel.

Это трехпанельная система, но не копия donor-подхода. Здесь у каждой панели строгое продуктовое назначение.

## Левый sidebar

Sidebar состоит из двух уровней.

### 1. Structure navigator

Верхняя часть sidebar показывает текущую структуру документа.

Что должно быть видно:

- порядок блоков,
- тип блока,
- смысловая категория,
- признак видимости в share-page.

Задача этой зоны:

- быстро сканировать narrative flow,
- понимать композицию документа,
- видеть, где не хватает opening, trust, strategy или CTA.

### 2. Block library

Нижняя часть sidebar показывает библиотеку блоков, сгруппированную по категориям.

Например:

- Открытие,
- Аудит,
- Контекст,
- Доверие,
- Стратегия,
- Процесс,
- Архитектура,
- Коммерция,
- Закрытие.

Для каждого блока в sidebar нужны:

- название,
- короткое описание,
- принадлежность к категории,
- быстрый action на добавление.

## Canvas

Canvas — это главный слой продукта.

Именно здесь proposal перестает быть “данными” и становится документом.

Canvas должен содержать:

- метаданные концепта,
- последовательность блоков,
- active block mode,
- редактор контента каждого блока,
- insertion zones между блоками.

### Роль canvas

Canvas не должен быть просто формой.

Его задача:

- удерживать narrative order,
- давать ощущение сборки реального pitch-документа,
- позволять быстро переставлять и вставлять blocks,
- поддерживать flow работы без переходов по экранам.

## Right panel

Right panel отвечает не за редактирование текста, а за delivery layer.

В него входят:

- статус публикации share-page,
- ссылка для клиента,
- просмотры,
- preview logic,
- правила текущего interaction mode.

Right panel должен удерживать мысль:

`мы собираем не внутреннюю форму, а клиентский артефакт`.

## Product interaction spec для вставки блоков

Механика вставки блоков должна работать на двух уровнях.

### 1. Добавление в конец

Это базовый action из block library.

Он нужен для быстрого наполнения структуры, когда порядок еще не критичен.

### 2. Вставка между блоками

Это ключевая mechanic для взрослого builder-а.

Между блоками должны существовать insertion zones.

Каждая insertion zone должна:

- быть визуально различимой,
- показывать действие `вставить после этого блока`,
- позволять добавить нужный тип блока без ручной перестановки всей структуры.

Именно эта mechanic приближает builder к presentation workflow и уводит его от ощущения линейной админки.

### 3. Quick insert

Insertion zone не должна быть только технической строкой кнопок.

Для взрослого UX в ней должны существовать два уровня выбора:

- recommended blocks для текущей narrative-точки,
- полный каталог блоков по категориям.

Это позволяет одновременно:

- ускорять сборку,
- подсказывать правильную структуру,
- не ограничивать пользователя жестким сценарием.

## Что считается хорошим UX для insertion zones

1. Пользователь видит точку вставки до первого блока.
2. Пользователь видит точку вставки после каждого блока.
3. Вставка должна быть быстрым action, а не отдельным модальным окном.
4. После вставки новый block должен появляться именно в выбранной позиции.
5. Перестановка вверх/вниз остается как вспомогательная mechanic, но не как единственный способ управления порядком.

## Базовые interaction mode в MVP

На первом этапе builder поддерживает такие режимы взаимодействия:

### 1. Structure mode

Пользователь думает о порядке narrative-блоков.

Основные действия:

- добавить block,
- вставить block,
- удалить block,
- поднять/опустить block.

### 2. Content mode

Пользователь заполняет конкретный block.

В MVP этот режим реализуется как active block mode:

- в canvas подробно открыт только один block,
- остальные блоки показываются в compact mode,
- выбор active block происходит из structure navigator или из самого canvas.

Основные действия:

- headline,
- body,
- bullets,
- metrics,
- CTA,
- visibility.

### 3. Delivery mode

Пользователь публикует document как client-facing artifact.

Основные действия:

- опубликовать share-page,
- открыть ссылку,
- проверить preview logic,
- отслеживать просмотры.

## Что уже начинаем внедрять

В текущем этапе разработки в builder уже запускаются такие изменения:

- sidebar с navigator + block library,
- категории у block templates,
- canvas как основной слой документа,
- active block mode,
- insertion zones между блоками,
- quick insert с recommended blocks и полным каталогом,
- right panel как delivery-слой.

Это еще не финальная luxury-версия интерфейса, но уже правильная product-direction основа.
