# Domain Model MVP

## Назначение

Этот документ фиксирует первую рабочую модель данных для MVP. Задача модели проста: обеспечить базовый sales loop без перегрузки второстепенными сущностями.

Базовый loop:

1. Менеджер создает компанию.
2. Для компании создается proposal.
3. В proposal загружаются media assets.
4. Для proposal выпускается share-link.
5. Клиент открывает ссылку, а система учитывает просмотры.

## Сущности

### companies

Главная карточка компании-клиента.

Минимальный смысл:

- хранит исходный контекст для продажи,
- является корнем для proposal,
- помогает вести pipeline по статусам.

Ключевые поля:

- `name`
- `website_url`
- `industry`
- `short_description`
- `contacts`
- `notes`
- `status`

Статусы:

- `draft`
- `research`
- `concept`
- `sent`
- `opened`
- `won`
- `archived`

### proposals

Основной digital-концепт для компании.

Минимальный смысл:

- хранит визуальное и стратегическое предложение,
- управляет сборкой блоков,
- становится источником для share-page и PDF.

Ключевые поля:

- `title`
- `preset`
- `status`
- `headline`
- `subheadline`
- `cta_label`
- `structure`
- `settings`

Поле `structure` является ядром builder-модели. Оно хранит массив блоков концепта в JSON-формате.

Каждый блок содержит:

- `id`
- `type`
- `title`
- `visible`
- `payload`

Подробная структура block payload и каталог блоков зафиксированы в `docs/BUILDER-SYSTEM.md`.

Пресеты:

- `industrial-dark`
- `tech-blue`
- `premium-light`
- `heavy-industry`
- `engineering-pro`
- `metal-tech`

### assets

Медиаматериалы, привязанные к proposal.

Минимальный смысл:

- дают единое место для изображений, видео, PDF и logo assets,
- позволяют потом строить медиабиблиотеку без миграции базовой модели.

Ключевые поля:

- `kind`
- `storage_bucket`
- `storage_path`
- `file_name`
- `mime_type`
- `alt_text`
- `source`
- `metadata`

В MVP `assets` остаются универсальной таблицей для трех сценариев:

- фото компании и производства,
- видео и презентационные media embeds,
- документы и будущие PDF-экспорты.

Отдельные таблицы media collections, galleries и AI-generated outputs пока не нужны. Они могут быть добавлены позже поверх этого слоя.

### share_links

Публичные ссылки для клиента.

Минимальный смысл:

- отделяют внутренний workspace от клиентской презентации,
- позволяют считать просмотры,
- дают базу для аналитики и срока действия ссылки.

Ключевые поля:

- `token`
- `slug`
- `status`
- `expires_at`
- `view_count`
- `last_opened_at`

## Связи

- одна `company` может иметь несколько `proposal`
- один `proposal` может иметь несколько `asset`
- один `proposal` может иметь несколько `share_link`

## Владение данными

На текущем этапе все сущности принадлежат одному владельцу и одному администратору системы.

Это нужно для двух вещей:

- сохранить максимально простую модель доступа,
- не усложнять продукт многопользовательской логикой раньше времени.

## Почему модель именно такая

В MVP нам важен не “полный digital factory”, а минимальный, но сильный сценарий продажи. Поэтому в модель пока не включены:

- отдельные таблицы блоков proposal,
- шаблоны и marketplace presets,
- детальная event-аналитика,
- AI jobs,
- workflow approvals,
- billing.

При этом builder уже опирается на `proposal.structure` как на основную рабочую сущность. Поэтому модель сознательно хранит блоки внутри `proposal`, а не выносит их в отдельные relational таблицы на первом этапе.

Все эти слои можно добавить позже поверх текущего ядра, не ломая первую модель данных.
