# MARKET BENCHMARK DATA SOURCES

## Цель документа
Зафиксировать, откуда модуль market benchmark может получать данные, какие данные считать надежными, а какие считать условными и вводить только после проверки.

Главный принцип:
benchmark нельзя строить на фантазиях о данных.

Нужно четко разделять:
- что мы гарантированно берем из Avito API;
- что мы можем брать из публичной выдачи;
- что мы считаем локально внутри сервиса;
- где есть продуктовый и юридический риск.

## Слои источников данных

### Слой 1. Данные собственного аккаунта через Avito API
Это самый надежный источник.

Отсюда мы можем брать:
- список собственных объявлений;
- поля объявления;
- фото и порядок изображений;
- базовые метрики;
- статусы;
- динамику по своим объявлениям.

Что это дает benchmark-модулю:
- качественную базу для сравнения объявления пользователя с эталоном;
- точные данные для режима “до/после правок”.

Ограничение:
этот слой почти не закрывает прямую конкурентную аналитику по чужим объявлениям.

### Слой 2. Публичная выдача и открытые карточки
Это потенциальный источник для поиска похожих объявлений и построения рыночных паттернов.

Из него можно извлекать:
- заголовки;
- цены;
- город;
- категорию;
- миниатюры и визуальные паттерны;
- наличие инфографики;
- количество фото, если это доступно публично;
- общую структуру карточки.

Что это дает benchmark-модулю:
- сравнение объявления пользователя с похожими предложениями;
- формирование эталонов по нише и городу;
- визуальный benchmark по фото и инфографике.

Ограничения:
- стабильность источника не гарантирована;
- доступность полей может меняться;
- нельзя строить весь продукт на этом без валидации.

### Слой 3. Локально вычисляемые признаки сервиса
Это слой, который мы считаем сами на основе импортированных и собранных данных.

Примеры:
- score заголовка;
- score первого фото;
- score инфографики;
- признаки конкретности;
- признаки перегруза текстом;
- сигналы визуальной чистоты;
- позиция относительно внутреннего эталона.

Что это дает benchmark-модулю:
- объяснимость;
- устойчивость логики;
- независимость от "магии".

### Слой 4. Внутренние эталоны по нишам
Это curated-слой продукта.

Примеры:
- эталон сильной карточки для услуг;
- эталон сильного первого фото для недвижимости;
- эталон перегруженной и чистой инфографики;
- типовые паттерны выигрышных офферов по нишам.

Что это дает benchmark-модулю:
- доменную экспертность;
- более полезные рекомендации, чем простая статистика по рынку.

## Какие данные можно использовать уже в раннем benchmark

### Надежно использовать
- свои объявления и их метрики из Avito API;
- локально вычисленные score и признаки;
- внутренние эталоны сервиса;
- агрегированные паттерны по вручную проверенным кейсам.

### Использовать осторожно
- похожие объявления из публичной выдачи;
- визуальные признаки публичных карточек;
- цены и заголовки в рыночной выборке.

### Не считать основой первой версии
- обещания полной конкурентной аналитики по API;
- выводы, если выборка слишком узкая или нерелевантная;
- любые сигналы, которые нельзя объяснить пользователю.

## Минимальная модель benchmark-данных

### 1. Набор benchmark-запросов
Сущность: `acb_benchmark_queries`

Назначение:
хранить пользовательский контекст сравнения.

Поля:
- `id`
- `user_id`
- `listing_id` - nullable, если benchmark строится без привязки к конкретному объявлению.
- `city`
- `region`
- `category_name`
- `service_name`
- `price_min`
- `price_max`
- `query_mode` - `market`, `similar_listings`, `city_service`.
- `created_at`

### 2. Снимок benchmark-результата
Сущность: `acb_benchmark_snapshots`

Назначение:
хранить итог сравнения на конкретный момент времени.

Поля:
- `id`
- `query_id`
- `listing_id`
- `benchmark_score`
- `title_gap_score`
- `photo_gap_score`
- `infographic_gap_score`
- `offer_gap_score`
- `price_gap_score`
- `summary`
- `created_at`

### 3. Рыночные разрывы
Сущность: `acb_benchmark_gaps`

Назначение:
хранить конкретные разрывы между объявлением пользователя и рыночным benchmark.

Поля:
- `id`
- `snapshot_id`
- `zone` - `title`, `photo`, `infographic`, `offer`, `price`.
- `gap_direction` - `below`, `equal`, `above`.
- `gap_score`
- `title`
- `description`
- `recommendation`
- `sort_order`
- `created_at`

### 4. Паттерны рынка
Сущность: `acb_benchmark_patterns`

Назначение:
хранить агрегированные признаки рынка по выборке.

Поля:
- `id`
- `snapshot_id`
- `pattern_type` - `title`, `photo`, `infographic`, `price`, `offer`.
- `pattern_key`
- `pattern_value`
- `confidence_level`
- `sample_size`
- `created_at`

### 5. Похожие объявления
Сущность: `acb_benchmark_samples`

Назначение:
хранить примеры карточек, на основе которых строится benchmark.

Поля:
- `id`
- `snapshot_id`
- `external_url`
- `title`
- `price_value`
- `city`
- `source_type` - `public`, `manual`, `internal`.
- `is_reference`
- `created_at`

## Как использовать benchmark без самообмана

### Правило 1
Сначала сравниваем с внутренним эталоном, а не с произвольными конкурентами.

### Правило 2
Если выборка похожих объявлений недостаточна, сервис должен честно это показывать.

### Правило 3
Каждый вывод benchmark должен опираться на:
- размер выборки;
- понятный признак;
- объяснение простым языком.
- структурированный gap, а не только общую цифру.

### Правило 4
Если источник данных нестабилен, benchmark не должен быть единственным основанием для жестких рекомендаций.

## Что делать в первой версии
Первая взрослая версия benchmark должна опираться на три вещи:
- внутренние эталоны по нишам;
- собственные данные пользователя из Avito API;
- ограниченный набор похожих объявлений по публичной выдаче только после валидации.

## Итог
Benchmark-модуль должен строиться как слой объяснимого сравнения с рынком, а не как хаотичный сбор чужих объявлений.

Если держать эту дисциплину, модуль станет сильным отличием продукта. Если нет, он быстро превратится в шумную, но слабую фичу.
