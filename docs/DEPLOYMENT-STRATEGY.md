# DEPLOYMENT STRATEGY

Стратегия разработки и выката для AVITO CONVERSION BUILDER.

## 1. Текущее состояние проекта

Сейчас проект развивается в production-like окружении.

Это означает:
- часть изменений сразу попадает в рабочий контур домена;
- статические страницы и документация могут быть видны пользователю сразу после правки;
- backend, OAuth, БД и интеграции нельзя менять без release-дисциплины.

Вывод: проект уже нельзя вести как набор случайных файлов на сервере. Для core-части нужен нормальный git-контур, GitHub как внешний источник истории и понятные правила релиза.

## 2. Что считаем source of truth

На текущем этапе:
- локальная рабочая копия на сервере — место фактической разработки;
- GitHub-репозиторий — внешний backup истории и контроль изменений;
- CHANGELOG.md — краткая фиксация фактических изменений;
- README.md, AGENTS.md, PROJECT-DEVELOPMENT-PLAN.md, DEVELOPMENT-CALENDAR.md — управленческий контур проекта.

Целевая модель:
- git-репозиторий в корне проекта обязателен;
- GitHub используется как основной удаленный origin;
- любые значимые изменения сначала фиксируются в git, потом считаются частью рабочего контура;
- production не должен быть единственным местом, где существует актуальный код.

## 3. Категории изменений и правила выката

### A. Безопасные изменения

Что входит:
- документация;
- контентные правки;
- статические страницы лендинга;
- тексты, секции, ссылки, визуальные улучшения без изменения backend-логики.

Как работаем:
1. Вносим изменение.
2. Проверяем страницу или документ.
3. Обновляем CHANGELOG.md.
4. Фиксируем в git.
5. Пушим в GitHub.

Для этой категории отдельный staging не обязателен, если не ломается публичный сценарий.

### B. Релизные изменения среднего риска

Что входит:
- кабинет;
- frontend-логика приложения;
- API endpoints без миграций;
- auth flow;
- интеграционная логика без destructive-операций.

Как работаем:
1. Сначала читаем RUNBOOK и RELEASE-CHECKLIST.
2. Делаем изменение маленькой порцией.
3. Проверяем затронутый сценарий локально в текущем контуре.
4. Обновляем docs и CHANGELOG.md.
5. Фиксируем в git.
6. Пушим в GitHub.
7. Сразу после выката проверяем health и основной пользовательский сценарий.

### C. Критические изменения

Что входит:
- SQL-миграции;
- изменение схемы хранения;
- OAuth и token lifecycle;
- Avito integration;
- логика, способная сломать доступ в кабинет или данные.

Как работаем:
1. До изменений делаем backup или убеждаемся, что он существует.
2. Проверяем rollback path.
3. Применяем изменение только как отдельный релизный шаг.
4. После изменения проверяем health endpoint, auth flow и основной сценарий.
5. Если есть риск нестабильности, сначала выносим задачу в staging-план, а не правим напрямую production-like контур.

## 4. Что делать прямо сейчас

На текущем этапе проекта правильный взрослый режим такой:
- заводим git в корне проекта;
- подключаем GitHub-репозиторий как origin;
- используем GitHub как зеркало и историю изменений;
- не делаем большие backend-правки без release-подхода;
- для простых landing/docs-изменений допускаем прямую работу в текущем контуре;
- для API/SQL/OAuth считаем, что у нас mini-release процесс.

## 5. Минимальный git-процесс

Пока команда маленькая, достаточно такого процесса:
1. Сделать изменение.
2. Проверить, что затронутый сценарий работает.
3. Обновить CHANGELOG.md и нужные docs.
4. Посмотреть diff и убедиться, что нет лишних файлов.
5. Сделать commit с нормальным сообщением.
6. Пушить в GitHub.

Примеры нормальных сообщений commit:
- add privacy policy page and footer link
- document agent workflow and development calendar
- add audit backend endpoint and wire cabinet audit view

## 6. Что GitHub дает проекту уже сейчас

GitHub нужен не только для кода, но и как:
- резервная история изменений;
- защита от потери текущего состояния на сервере;
- база для будущего CI/CD;
- точка сборки staging и release-процесса;
- место, где видно, что именно и когда менялось.

## 7. Что не считаем зрелым процессом

Плохой режим для этого проекта:
- править production-like сервер без git-истории;
- не фиксировать docs и changelog;
- вносить SQL и auth-изменения без rollback-понимания;
- хранить единственную актуальную версию только на сервере;
- выкатывать большие изменения без проверки ключевого сценария.

## 8. Следующий зрелый шаг

Следующая цель процесса:
- поднять staging-контур;
- отрабатывать risky backend changes сначала там;
- после этого выкатывать в production по упрощенному release-flow.

Пока staging нет, production-like контур можно использовать только при дисциплине:
- маленькие изменения;
- понятный rollback;
- changelog;
- git;
- пост-проверка.
