# Builder System

## Зачем нужен этот документ

Этот документ фиксирует proposal builder как ядро продукта. Его задача — не просто хранить данные компании, а собирать живой продающий документ, который можно:

- редактировать по блокам,
- усиливать через AI,
- наполнять фото и видео,
- публиковать как share-page,
- позже экспортировать в PDF.

## Главный принцип

Builder — это не конструктор сайта и не CMS-панель.

Builder — это рабочее пространство для сборки персонального digital-концепта компании.

Пользователь должен чувствовать, что он собирает новую версию бизнеса для клиента, а не просто редактирует поля в базе.

## Базовый состав builder

Proposal builder строится вокруг трех слоев:

1. блочная структура документа,
2. AI-помощник для текста,
3. медиаслой для фото и видео.

Именно это сочетание делает продукт сильным.

Подробная схема block library, категорий, обязательных метаданных и visual/presentation режимов вынесена в `docs/BLOCK-LIBRARY-SCHEMA.md`.

## Типы блоков MVP

На первом рабочем этапе в системе уже поддерживаются такие группы блоков:

- opening и context,
- audit и SEO,
- strategy,
- trust,
- media,
- industrial,
- process и commercial closing.

Текущий live-набор включает такие типы:

### `hero`

Роль:

- первый экран концепта,
- сильное обещание,
- framing всего документа.

### `company-overview`

Роль:

- кто компания,
- чем занимается,
- в каком контексте работает,
- что важно подчеркнуть в новой подаче.

### `offer`

Роль:

- показать, что предлагается клиенту,
- перевести разговор из «сайт» в «цифровая упаковка».

### `pain-points`

Роль:

- зафиксировать слабые места текущего сайта,
- дать аргументированный аудит,
- создать точку для продажи нового решения.

### `website-audit`

Роль:

- формально показать слабые места текущего сайта,
- зафиксировать UX, visual и mobile-проблемы,
- создать более сильную audit-рамку для новой подачи.

### `competitor-gap`

Роль:

- показать отставание от сильной конкурентной digital-подачи,
- перевести обсуждение в рыночный контекст,
- усилить аргументацию к redesign.

### `seo-growth-map`

Роль:

- показать потенциал поискового роста,
- объяснить будущую SEO-архитектуру,
- связать redesign и growth logic.

### `solution`

Роль:

- описать логику новой подачи,
- показать, как изменится восприятие компании,
- связать визуал, структуру и продажи.

### `digital-transformation`

Роль:

- показать, как меняется восприятие компании после redesign,
- продать новый digital-образ бизнеса,
- связать визуальные изменения с бизнес-эффектом.

### `lead-strategy`

Роль:

- объяснить сценарии захвата и конверсии,
- показать логику CTA,
- связать структуру сайта с next step клиента.

### `proof`

Роль:

- усилить доверие,
- показать цифры, кейсы, производственные мощности, сертификаты, географию.

### `company-metrics`

Роль:

- показать масштаб бизнеса через цифры,
- сделать trust-слой более конкретным,
- усилить восприятие компании как серьезного игрока.

### `certificates`

Роль:

- показать стандарты, лицензии и нормативность,
- усилить решение закупщика,
- перевести доверие в подтверждаемые факты.

### `roadmap`

Роль:

- показать этапы проекта,
- сделать процесс понятным и управляемым,
- снизить тревожность клиента.

### `website-structure`

Роль:

- показать будущую архитектуру сайта,
- объяснить, какие разделы будут собраны,
- сделать объем проекта осязаемым.

### `industrial-gallery`

Роль:

- дать место для визуального образа производства,
- показать оборудование, цеха и процесс,
- усилить ощущение масштаба через media.

### `before-after`

Роль:

- показать контраст между текущим и новым digital-образом,
- визуально продать transformation effect,
- усилить аргумент на redesign.

### `commercial-offer`

Роль:

- кратко фиксировать формат работы,
- диапазон стоимости,
- коммерческую рамку проекта.

### `factory-scale`

Роль:

- показать физический масштаб производства,
- зафиксировать инфраструктуру как trust-аргумент,
- усилить industrial-характер документа.

### `technology`

Роль:

- раскрыть технологическую базу компании,
- показать оборудование и процессы,
- усилить образ инженерной зрелости.

### `quality-control`

Роль:

- показать систему качества,
- зафиксировать управляемость результата,
- усилить доверие в инженерном B2B.

### `cta`

Роль:

- завершить документ понятным следующим шагом,
- перевести клиента в созвон, обсуждение или запуск.

Это не окончательная библиотека блоков продукта, а только минимальный первый состав для работающего MVP. Расширенная система категорий и block family зафиксирована отдельно в `docs/BLOCK-LIBRARY-SCHEMA.md`.

## Поля каждого блока

Каждый блок в `proposal.structure` хранится как JSON-объект.

Обязательный каркас блока:

- `id` — уникальный идентификатор блока,
- `type` — тип блока,
- `title` — внутреннее название в builder,
- `visible` — участвует ли блок в share-page,
- `payload` — содержимое блока.

### Базовый состав `payload`

- `eyebrow` — короткая надстрока,
- `headline` — основной заголовок блока,
- `body` — основной текст,
- `bullets` — список тезисов,
- `metrics` — набор пар `label/value`,
- `ctaLabel` — подпись кнопки,
- `ctaHref` — ссылка CTA.

Этого состава достаточно, чтобы покрыть первый сильный цикл без перегруза интерфейса.

Для полной block library дополнительно нужны catalog-level метаданные: `description`, `category`, `icon`, `preview_image`, `tags`, `schema`, `variants`, `dark_mode_support`, `pdf_support`, `mobile_support`, `animations`. Они зафиксированы в `docs/BLOCK-LIBRARY-SCHEMA.md`.

## Внешняя нейроподдержка вне runtime

В текущем MVP AI-слой убран из живого интерфейса builder.

Причина простая: интерактивная генерация внутри редактора делала продукт нестабильным и мешала основному сценарию ручной сборки концепта.

Текущий принцип такой:

- builder остается ручным и предсказуемым,
- редактор блока не зависит от локальной модели,
- тексты, тест-кейсы и черновые идеи можно готовить внешними нейросетями вне продукта,
- в интерфейс попадает уже проверенный человеком результат.

Если AI вернется позже, его нужно внедрять только как необязательный асинхронный слой, а не как обязательную кнопку внутри формы.

## Как устроить фото/видео слой без перегруза MVP

## Принцип медиаслоя

Фото и видео нужны не ради декора, а ради доверия.

В контексте производственных компаний медиа должны показывать:

- производство,
- оборудование,
- продукцию,
- объекты,
- команду,
- процесс,
- масштаб бизнеса.

## Что нужно поддержать на MVP

### Фото

Нужны сценарии:

- загрузка вручную,
- выбор главного изображения блока,
- несколько изображений для proof или gallery-like подачи,
- подпись и alt text.

### Видео

На MVP не нужен сложный video DAM.

Достаточно поддержать:

- внешнюю ссылку на видео,
- встраивание YouTube или RuTube,
- одно превью-изображение,
- краткую подпись.

### Документы

Нужно оставить место для:

- PDF-презентации,
- аудита,
- коммерческого приложения.

## MVP-правило против перегруза

Не делать сразу отдельную медиабиблиотеку уровня Directus.

На первом этапе достаточно:

- таблицы `assets`,
- привязки asset к `proposal`,
- простых сценариев загрузки и выбора,
- отображения медиа в builder и share-page.

## Что не нужно делать сразу

- версионирование файлов,
- сложные папки и коллекции,
- AI-генерацию изображений внутри MVP-редактора,
- кроп и глубокий editor для media,
- отдельный backoffice для ассетов.

Это можно добавить позже, когда сам builder и share-page уже начнут давать продажи.

## Приоритет реализации

Если двигаться без лишней сложности, порядок должен быть такой:

1. довести builder до стабильной блочной работы,
2. добавить базовый медиаслой фото и видео,
3. встроить Ollama для генерации и улучшения текстов,
4. только потом расширять PDF и более сложную media automation.

## Итоговая формула

Сильный MVP builder для этого проекта — это:

- гибкие блоки,
- ручная редактура смыслов,
- AI-помощь для ускорения текста,
- реальные фото и видео,
- живая share-page по URL.

## Архитектурный поворот: переход на V3-редактор (июнь 2026)

### Суть перехода

До этого момента редактор существовал в двух версиях одновременно — V2 и V3.
V2 — оригинальная карточная система с оверлейными кнопками управления прямо на холсте.
V3 — трёхпанельный document builder, построенный с нуля.

После этого поворота **V3 — единственная рабочая версия для всех новых концептов.**
V2 продолжает существовать в кодовой базе только как legacy-слой для совместимости со старыми записями.

### Новая архитектура редактора (V3)

Файл: `src/components/builder/editor-canvas-v3.tsx`

**Трёхпанельный layout:**

```
┌────────────────────────────────────────────────────────────┐
│  STRUCTURE PANEL  │       CANVAS (iframe)       │  PROPS   │
│  (левая панель)   │   (живой рендер документа)  │ (правая) │
│                   │                             │          │
│  ── hero          │  ┌─ Блок: hero ──────────┐  │  [поля]  │
│  ── company …     │  │  Заголовок             │  │          │
│  ── offer         │  │  Подзаголовок          │  │          │
│     ↑ ↓ ×         │  └────────────────────────┘  │          │
└────────────────────────────────────────────────────────────┘
```

- **Левая панель (structure panel)**: список блоков в порядке документа. Кнопки управления (↑, ↓, ×) вынесены именно сюда — на холсте никаких оверлеев нет.
- **Центральный холст**: живой рендер документа через `<iframe>` с изолированными стилями (`src/lib/proposal-html-renderer.ts`).
- **Правая панель (props panel)**: форма редактирования активного блока — поля, переключатели, rich-text через TipTap.

**CSS-неймспейс V3:**
- `.ev3-*` — элементы интерфейса редактора (панели, хедер, кнопки)
- `.dv3-*` — классы внутри документных блоков (light-theme TipTap)

### Логика загрузки версии редактора

Файл: `src/app/dashboard/proposals/[proposalId]/page.tsx`

```ts
// По умолчанию — V3
const [editorVersion, setEditorVersion] = useState<"v2" | "v3">("v3");

// Auto-detect legacy: если ВСЕ блоки не начинаются с "doc-" → это V2-документ
if (blocks.length > 0 && blocks.every((b) => !b.type.startsWith("doc-"))) {
  setEditorVersion("v2");
}
```

- Новые концепты → V3 сразу
- Старые концепты (V2-блоки) → автоматически открываются в V2
- Кнопка миграции «→ V3» отображается только когда открыт V2-документ (одностороннее)

### Типы блоков

- **V2-блоки**: старый набор — `hero`, `company-overview`, `offer`, `pain-points`, `website-audit` и др. (без префикса `doc-`)
- **V3-блоки**: все новые блоки начинаются с префикса `doc-` — `doc-hero`, `doc-text`, `doc-quote`, `doc-media`, `doc-divider` и т.д.

Префикс `doc-` — главный маркер принадлежности к V3-системе. Именно по нему происходит auto-detect версии редактора.

### Где хранятся шаблоны и метаданные блоков

- `src/types/domain.ts` — типы `ProposalBlockType`, `ProposalBlockPayload`
- `src/lib/proposal-builder.ts` — `proposalBlockSemanticMetadata`, `proposalBlockTemplates`, `normalizeProposalBlocks`
- `src/lib/proposal-html-renderer.ts` — HTML-рендер блоков + inline CSS для iframe-холста
- `src/components/share/block-renderers.tsx` — рендер блоков на share-странице

### Добавление нового блока

Обязательный порядок шагов зафиксирован в `docs/BLOCK-AUTHORING-GUIDE.md`. Основная точка входа — именно этот файл.

## Архитектурный поворот: единый дашборд (июнь 2026)

### Суть перехода

До этого момента дашборд работал в двух режимах: «Компании» и «Концепты» — переключаемые через URL-параметр `?mode=`.

После перехода — **один список компаний с концептами внутри каждой.** Никаких режимов, никакого дублирования.

Файл: `src/app/dashboard/page.tsx`

### Новая структура дашборда

```
┌──────────────────────────────────────────────────────┐
│  FPB / Компании и концепты          [Выйти] [...]    │
├──────────────────────────────────────────────────────┤
│  Компании: 12   Концепты: 28   В работе: 5   ...     │
├──────────────────────────────────────────────────────┤
│  + Добавить компанию  (раскрываемая форма)           │
├──────────────────────────────────────────────────────┤
│  [Активные·12] [В работе·3] [Архив·2] [Все·14]      │
├──────────────────────────────────────────────────────┤
│  ООО Промтех  [В работе]  3 конц. 👁14 💬2  [Архив] │
│    └ Аудит сайта  [Черновик]  👁5  [Редактор] [Share]│
│    └ Новый концепт...                    [Создать]   │
│      Редактировать компанию (раскрывается)           │
│ ─────────────────────────────────────────────────────│
│  СпецМаш       [Новый]   1 конц.  ...                │
└──────────────────────────────────────────────────────┘
```

### Удалённые сущности

В процессе перехода полностью удалены из `page.tsx`:
- тип `DashboardMode`
- тип `ProposalFilter`
- функция `getDashboardMode()`
- функция `getProposalFilter()`
- параметр `mode` из `buildDashboardHref()`
- секция выбора режима («Режим кабинета»)
- отдельный раздел «Концепты» (proposal cards с полной статистикой)

### Новые CSS-классы дашборда

Все в `src/app/globals.css` в блоке `/* DB COMPANY BLOCK */`:
- `.db-company-block` — блок-обёртка одной компании
- `.db-proposal-row` — строка концепта внутри компании
- `.db-proposal-title` — ссылка на редактор концепта
- `.db-proposal-indent` — отступный символ `└` / `+`
- `.db-add-proposal` — инлайн-форма добавления концепта
- `.db-quick-add` — раскрываемая форма добавления компании
- `.db-status--p-*` — бейджи статусов концептов (префикс `p-` чтобы не конфликтовать с компанейскими)

### Фильтрация

Только по статусу компании через URL `?companyStatus=`. Значение `active` — по умолчанию, из URL опускается.
Концепты показываются все — внутри своей компании, без дополнительной фильтрации.

Именно такая комбинация делает систему не просто редактором, а сильным инструментом продажи digital-упаковки для производственных компаний.
