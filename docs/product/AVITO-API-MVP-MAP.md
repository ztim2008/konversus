# AVITO API MVP MAP

## Зачем этот документ
Этот документ фиксирует, как именно строить MVP на базе Avito API без расползания в бесконечный комбайн.

Главный принцип:
Avito API - это двигатель продукта, а не его витрина.

Пользователь покупает не доступ к API, а понятные рабочие сценарии поверх API.

## Продуктовая формула MVP
Подключил аккаунт Avito -> увидел все объявления в одном кабинете -> получил список проседающих объявлений -> открыл аудит текста и фото -> сделал улучшенную версию -> увидел, стало ли лучше.

## Что продаем как первую ценность
- единый кабинет объявлений;
- автоматическое выявление просадок;
- аудит объявления без ручной рутины;
- понятные рекомендации по тексту, фото и инфографике;
- история правок и отчетность для клиента.

## Главные сценарии MVP

### Сценарий 1. Подключение аккаунта и импорт объявлений
Что получает пользователь:
- подключает свой аккаунт Avito;
- видит все объявления в одном кабинете;
- не собирает данные вручную по разным вкладкам.

Почему это важно:
это создает постоянную рабочую среду, а не разовый сервис по генерации текста.

### Сценарий 2. Подсветка проседающих объявлений
Что получает пользователь:
- система показывает, какие объявления требуют внимания в первую очередь;
- пользователь не тратит время на просмотр всего массива вручную.

Почему это важно:
ценность начинается не с редактирования, а с приоритизации.

### Сценарий 3. Аудит объявления
Что получает пользователь:
- score объявления;
- список проблем;
- объяснение, почему это проблема;
- рекомендации в порядке приоритета.

Почему это важно:
именно здесь возникает первый AHA-moment.

### Сценарий 4. Улучшение объявления
Что получает пользователь:
- улучшенную версию текста;
- рекомендации по замене или усилению фото;
- рекомендации по инфографике;
- основу для новой версии объявления.

Почему это важно:
аудит без действия быстро превращается в красивый, но бесполезный отчет.

### Сценарий 5. Контроль результата
Что получает пользователь:
- видно, что изменилось после правок;
- видно, какие гипотезы сработали;
- агентство может показать клиенту краткий отчет без ручной сборки.

Почему это важно:
именно здесь продукт превращается в инструмент удержания, а не разовую консультацию.

## Что брать из Avito API в первую очередь

### P0. Подключение аккаунта
- авторизация и связка аккаунта с пользователем сервиса;
- хранение токенов и безопасное обновление доступа;
- проверка здоровья подключения.

Результат:
пользователь вообще может начать работать с данными, а не с ручным копированием.

### P0. Импорт объявлений
- список объявлений;
- базовые поля объявлений;
- статусы и служебные признаки, нужные для кабинета;
- регулярная синхронизация в локальную модель сервиса.

Результат:
есть единый кабинет объявлений как база всех следующих сценариев.

### P1. Метрики по объявлениям
- просмотры;
- контакты;
- базовые показатели для приоритизации;
- история изменений по времени.

Результат:
можно подсвечивать просадки и показывать динамику после правок.

### P1. Данные для аудита
- заголовок;
- описание;
- цена;
- категория и базовые параметры;
- фото и порядок изображений.

Результат:
достаточно данных, чтобы строить аудит текста и визуала.

### P2. Обновление объявления
- возможность передать улучшенные данные обратно;
- создание безопасного сценария редактирования без ручного хаоса.

Результат:
сервис замыкает цикл не только на анализе, но и на действии.

## Что не брать в первый MVP
- все методы Avito API подряд;
- глубокую автоматизацию публикации всех сущностей сразу;
- сложные агентские multi-account сценарии с первого дня;
- тяжелую оркестрацию A/B как обязательную первую фичу;
- аналитику конкурентов, если она зависит от нестабильных или неподтвержденных источников.

## Как приоритизировать модули

### Модуль A. Data Hub
Состав:
- подключение аккаунта;
- импорт объявлений;
- нормализация данных;
- синхронизация.

Приоритет: максимальный.

### Модуль B. Audit Engine
Состав:
- score текста;
- score фото;
- score инфографики;
- причины просадки;
- список правок.

Приоритет: максимальный.

### Модуль C. Improvement Workspace
Состав:
- улучшенная версия текста;
- визуальные рекомендации;
- история изменений;
- подготовка обновления.

Приоритет: высокий.

### Модуль D. Results Layer
Состав:
- динамика метрик;
- сравнение до и после;
- короткий клиентский отчет.

Приоритет: высокий.

### Модуль E. Experimentation
Состав:
- A/B варианты;
- гипотезы;
- запуск режимов тестирования.

Приоритет: средний после стабилизации ядра.

## Что считать успехом первой версии
- пользователь подключил аккаунт без боли;
- увидел свои объявления в одном месте;
- быстро понял, что именно проседает;
- получил понятные правки;
- применил хотя бы одну рекомендацию;
- увидел изменение качества или метрик;
- захотел продолжить работу в сервисе.

## Ключевые риски

### Риск 1. Слишком широкий охват API
Симптом:
команда начинает строить платформенный слой вместо продукта.

Решение:
брать только те возможности API, которые прямо закрывают путь: импорт -> аудит -> улучшение -> контроль результата.

### Риск 2. Слабая продуктовая интерпретация данных
Симптом:
в кабинете много цифр, но мало решений.

Решение:
каждая метрика и каждое поле должны поддерживать конкретную рекомендацию или приоритизацию.

### Риск 3. Аудит превращается в общие советы
Симптом:
пользователь не видит разницы между сервисом и обычным чат-ботом.

Решение:
строить рекомендации на rule-based логике и доменных критериях, особенно по фото и инфографике.

### Риск 4. Перегрузка первого релиза
Симптом:
в первой версии слишком много экранов и мало пользы.

Решение:
первая версия должна отвечать на один главный вопрос: что у меня проседает и что исправить прямо сейчас.

## Решение по MVP
Первый релиз строим вокруг четырех обязательных вещей:
- подключение аккаунта Avito;
- импорт и единый кабинет объявлений;
- аудит текста, фото и инфографики;
- рекомендации и улучшенная версия с контролем результата.

Все остальное идет после стабилизации этого ядра.
