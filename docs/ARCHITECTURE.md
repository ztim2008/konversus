# Архитектура MVP

## Продуктовая рамка

Factory Proposal Builder — это внутренняя система для сборки premium digital-концептов, share-страниц и PDF-предложений для производственных компаний, инженерного B2B и industrial-сегмента.

Главный принцип: пользователь должен чувствовать, что он собирает digital-версию будущего компании, а не заполняет админку.

Продуктовый корень проекта зафиксирован в [docs/PROJECT-CONCEPT.md](docs/PROJECT-CONCEPT.md):

- новая цифровая упаковка для производств,
- продажа цифрового образа бизнеса, а не просто сайта,
- персонализированные концепты как главный коммерческий рычаг.

На текущем этапе продукт проектируется как личный закрытый кабинет владельца агентства. Командные роли, приглашения и многопользовательский режим в MVP не входят.

## Язык разработки

- Документация ведется на русском языке.
- Интерфейс ведется на русском языке.
- Внутренние продуктовые сущности описываются на русском языке.
- Технические идентификаторы в коде могут оставаться английскими, если так проще и чище для платформы.

## Решение по backend foundation

Для MVP выбрана локальная MySQL-база на сервере.

Причины:

- Не нужна зависимость от внешнего backend-провайдера и VPN-сценария.
- Проект должен стабильно работать в российском контуре.
- Один владелец и один админ не требуют внешнего auth-сервиса.
- Продукт строится вокруг кастомного UX и личного кабинета, а не вокруг SaaS-инфраструктуры.

## Почему не Directus в первой версии

Directus полезен, когда продукт в большой степени опирается на контентные сущности и backoffice-управление. Для текущего MVP это вторично.

Риск раннего Directus:

- продукт начнет тяготеть к CMS-модели,
- интерфейс будет подстраиваться под данные, а не под sales UX,
- команда раньше времени уйдет в backoffice и schema maintenance.

Directus можно подключить позже как отдельный слой для:

- шаблонов proposal,
- дизайн-пресетов,
- контентной витрины,
- внутренних справочников,
- медиабиблиотеки и backoffice-редактирования.

## Базовые сущности MVP

### company

Карточка компании-клиента.

Поля первого цикла:

- название,
- сайт,
- ниша,
- краткое описание,
- контакты,
- заметки,
- статус.

### proposal

Основной digital-концепт для конкретной компании.

Поля первого цикла:

- ссылка на company,
- название концепта,
- визуальный пресет,
- статус,
- структура блоков,
- дата обновления.

### asset

Медиафайлы проекта.

Поля первого цикла:

- ссылка на proposal,
- тип файла,
- путь в storage,
- подпись,
- источник.

### share_link

Публичная ссылка для клиента.

Поля первого цикла:

- ссылка на proposal,
- токен,
- статус,
- срок действия,
- количество просмотров,
- дата последнего открытия.

## Технические слои

### Next.js App Router

Отвечает за публичную витрину, внутренний workspace, маршрутизацию и server components.

### MySQL

Используется для:

- хранения компаний,
- хранения концептов,
- хранения asset и share-link данных,
- простого локального backend-контура.

### Локальная авторизация

Вместо внешнего auth используется локальный вход владельца:

- email и пароль хранятся в `.env.local`,
- сессия поддерживается через httpOnly cookie,
- закрытый кабинет отделен от публичных клиентских страниц.

## Логика авторизации для MVP

Авторизация сохраняется, но ее задача упрощена до минимума.

Она нужна для:

- защиты внутреннего кабинета,
- разделения закрытого кабинета и публичных share-page,
- безопасного создания компаний, концептов и ссылок,
- закрепления данных за одним владельцем.

Авторизация не используется для:

- командных ролей,
- приглашений пользователей,
- распределения прав между сотрудниками,
- сложного multi-workspace режима.

## Builder-first подход

Внутренний продукт больше не трактуется как обычный dashboard CRUD.

Системное ядро MVP теперь такое:

- `company` хранит контекст компании,
- `proposal` хранит стратегию, структуру блоков и состояние концепта,
- `share_link` превращает концепт в живую клиентскую страницу,
- `asset` обслуживает фото, видео, документы и будущий PDF.

Это означает, что главным экраном продукта должен стать proposal builder, а не только список сущностей.

Builder собирается вокруг трех слоев:

- блочная структура документа,
- ручное редактирование и сборка смыслов,
- медиаслой для фото и видео.

Без этих трех слоев продукт рискует превратиться либо в сухую админку, либо в обычную галерею без аргументации. Вместе они дают реальный sales-инструмент.

## Роль AI в текущей архитектуре

В текущем MVP AI не входит в runtime продукта.

Это осознанное решение: ручная сборка концепта должна работать стабильно и без зависимости от локальной модели, таймаутов и фоновой генерации.

Если AI вернется в продукт позже, его стоит выносить в отдельный необязательный асинхронный слой с очередью, кешем и явным ожиданием результата вне основного editor-flow.

## Что из концепта влияет на архитектуру

Из продуктовой концепции следуют несколько технических ограничений:

- публичная часть должна быть не маркетинговой заглушкой, а сильной продающей витриной агентства,
- внутренний интерфейс должен ощущаться как личный premium workspace владельца, а не как CRM или обычная админка,
- share-page и PDF являются не вторичным экспортом, а ядром sales-механики,
- шаблоны, пресеты и кейсы со временем станут отдельным системным слоем,
- архитектура должна поддерживать рост из агентского workflow в платформенный продукт.
