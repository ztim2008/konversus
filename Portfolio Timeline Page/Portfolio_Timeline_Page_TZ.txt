ТЗ: Portfolio Timeline Page для KONVERSUS
==============================================

Проект:
https://konversus.ru

Рабочая директория:
Portfolio Timeline Page

Файл задания:
Portfolio Timeline Page/Portfolio_Timeline_Page_TZ.txt

Цель:
Создать на Konversus отдельную страницу портфолио Алексея Тимофеева в формате современного dark Timeline Portfolio.

Страница должна использоваться как:
1. личное портфолио;
2. ссылка при откликах на вакансии;
3. ссылка для потенциальных клиентов;
4. постоянно пополняемый визуальный архив работ.

Главная идея:
НЕ делать обычную страницу "карточки проектов".
Нужен визуальный журнал работ: дата → короткая информация → большая визуальная композиция.

Референс по общей композиции:
timeline_portfolio_preview.jpg
На 2026-10-06 файла в репозитории нет. Если владелец положит его в эту директорию — смотреть композицию. Буквально не копировать.

Использовать идею:
- фиксированный левый профильный sidebar;
- вертикальная timeline;
- дата;
- краткое описание;
- крупный визуальный контент справа;
- последовательная лента работ;
- загрузка новых материалов при прокрутке.

Визуальный характер:
- только DARK MODE;
- современный editorial / portfolio / digital studio;
- минимализм;
- плотная типографика;
- много воздуха;
- без "AI SaaS" эстетики;
- без фиолетовых градиентов;
- без огромных rounded cards;
- без лишних декоративных элементов;
- интерфейс должен выглядеть как профессиональное портфолио дизайнера + AI engineer;
- визуальная часть работ должна быть главным акцентом.

Язык UI: русский.
Machine IDs, код, имена таблиц и полей: английский.

6. ЗАГРУЗКА ФОТО
==================================================

Главная UX-фича.

Алексей нажимает «+» и может:
- выбрать 1 изображение;
- выбрать несколько изображений;
- перетащить изображения drag & drop;
- загрузить изображения из файлового менеджера.

После загрузки изображения сразу появляются в preview.

Нужна возможность:
- менять порядок;
- удалить изображение;
- добавить ещё;
- видеть preview;
- сохранить.

Не делать сложный Photoshop-подобный редактор.
Практический потолок одной записи на MVP: до 12 изображений. Интерфейс не должен ломаться и на 1, и на 12.

==================================================
7. BENTO GALLERY
==================================================

Загруженные изображения автоматически раскладываются в красивую responsive Bento Grid.

Пример логики:

1 изображение:
┌────────────────────────────┐
│                            │
│          IMAGE             │
│                            │
└────────────────────────────┘

2 изображения:
┌──────────────┬─────────────┐
│              │             │
│      1       │      2      │
│              │             │
└──────────────┴─────────────┘

3 изображения:
┌────────────────┬───────────┐
│                │     2     │
│       1        ├───────────┤
│                │     3     │
└────────────────┴───────────┘

4+:
автоматическая современная Bento-композиция.
Порядок в сетке = sortOrder медиа. Первое изображение — самое крупное.

ВАЖНО:
Не превращать каждую запись в одинаковую сетку.
Layout должен зависеть от количества изображений и от их aspect ratio (width/height уже сохранены).

Нужна возможность красиво показывать:
- горизонтальные изображения;
- вертикальные;
- квадратные;
- screenshots;
- фотографии;
- UI;
- artwork.

Изображения не должны уродливо обрезаться.
object-fit: cover только внутри заранее известной ячейки с сохранёнными width/height, чтобы не было скачка вёрстки.
Для очень вертикальных кадров ячейка выше, а не квадратный кроп «в лоб».

8. LIGHTBOX
==================================================

При клике на изображение открывается fullscreen/lightbox.

Возможности:
- большое изображение;
- затемнение фона;
- стрелки ← →;
- клавиатура ← →;
- ESC;
- счётчик 1/7;
- переход между изображениями одной записи, не всего архива.

На мобильном:
- swipe;

Lightbox должен быть быстрым и минималистичным.
В lightbox грузится версия крупнее preview, не обязательно сырой оригинал, если оригинал тяжёлый.

9. EDITOR ДЛЯ ТЕКСТА
==================================================

Не нужен тяжёлый CMS editor.

Минималистичный rich text.

Разрешить только:
Bold
Italic
Link
Paragraph
Line break

Вставка ссылки:
выделил текст → Link → URL.

Например:

Создал AI-прототип для Konversus

где «Konversus» является ссылкой.

HTML/Markdown пользователю показывать НЕ надо.

В проекте уже есть TipTap: src/components/builder/tiptap-editor.tsx
Использовать тот же пакет @tiptap/*, не ставить второй editor.
Для этой формы собрать узкий экземпляр: StarterKit (жирный, курсив, абзац) + Link.
Не тащить в форму портфолио цвет, highlight, youtube, task list, выравнивание и картинки внутри текста.
Картинки работы живут только в media, не внутри description.

Хранить description как sanitized HTML.
На публичной странице рендерить только разрешённые теги: p, br, strong, em, a.
Ссылки: только http/https, rel="noopener noreferrer", target="_blank".

==================================================
10. INFINITE SCROLL
==================================================

На публичной странице записи загружаются постепенно.

Не загружать сразу всё портфолио.

initial: 12 entries
после достижения нижней точки: +12

Cursor-based pagination по (createdAt, id).
Не offset, чтобы новые публикации сверху не сдвигали страницу.

В конце, если записей больше нет, ничего лишнего не показывать.
Допустим тонкий индикатор загрузки. Текст «Loading...» в стиле чужого референса не использовать.

Черновики в публичную ленту не попадают.

==================================================
11. SORTING
==================================================

По умолчанию: createdAt DESC.
Новые работы сверху.
Самая свежая запись первой.

При удалении и редактировании порядок остальных не прыгает:
редактирование обновляет updatedAt, но место в ленте определяет createdAt.

sortOrder у entry в MVP не обязателен.
sortOrder обязателен у изображений внутри записи.

==================================================
12. DATABASE MODEL
==================================================

БД проекта: MySQL через mysql2, пул в src/lib/db.ts.
Prisma в этом репозитории для этих таблиц не заводить.
Новая технология и вторая БД запрещены.
Миграция — SQL-файл рядом с существующими sql/*.sql, следующим номером.

portfolio_entries
- id              CHAR(36) или BIGINT, в стиле соседних таблиц проекта
- title           VARCHAR(200) NOT NULL
- description     TEXT NULL          -- sanitized HTML
- created_at      DATETIME(3) NOT NULL
- updated_at      DATETIME(3) NOT NULL
- published       TINYINT(1) NOT NULL DEFAULT 0

portfolio_media
- id              как у entries
- entry_id        FK → portfolio_entries.id ON DELETE CASCADE
- url             VARCHAR(500) NOT NULL   -- preview / оптимизированная
- lightbox_url    VARCHAR(500) NOT NULL   -- крупная для лайтбокса
- thumb_url       VARCHAR(500) NULL
- width           INT NOT NULL
- height          INT NOT NULL
- alt             VARCHAR(300) NOT NULL DEFAULT ''
- sort_order      INT NOT NULL
- created_at      DATETIME(3) NOT NULL

Индекс публичной ленты: (published, created_at, id).
Индекс медиа: (entry_id, sort_order).

Если при изучении sql/ окажется общий стиль id другой — следовать ему, смысл полей не менять.

==================================================
13. IMAGE STORAGE
==================================================

Отдельный SaaS (Cloudinary, Uploadcare и аналоги) не подключать.

Уже есть локальная загрузка:
POST /api/upload
корень: sales-doc/uploads/YYYY/MM/
проверка админа: requireCurrentAdmin()
sharp уже в проекте, лимит картинки сейчас 8 МБ, MIME: jpeg/png/webp/gif, длинная сторона до 2000 px.

Для портфолио не переиспользовать этот endpoint «как есть» вслепую:
он один файл, кладёт в sales-doc и режет до 2000 px — для lightbox и bento этого мало как модели.

Сделать загрузку портфолио на том же диске и том же sharp:
каталог, например public-раздача через уже принятый в проекте способ отдачи uploads
(сейчас фото about отдаётся как /sales-doc/uploads/...).

На одно исходное изображение сохранять:
- оригинал (только на диске, в публичный bento не отдавать);
- lightbox: длинная сторона до 2400 px, WebP;
- preview для bento: длинная сторона до 1600 px, WebP;
- thumb: длинная сторона до 480 px, WebP.

Ширину и высоту писать из metadata sharp до кропа, чтобы bento знал пропорции.

Видео в MVP портфолио не принимать.

==================================================
16. DELETE
==================================================

Удаление записи требует подтверждения.

Удаление entry удаляет строки media (CASCADE) и файлы на диске:
оригинал, preview, lightbox, thumb.

Не оставлять осиротевшие файлы и строки.
Ошибка удаления файла логируется, строка в БД не должна указывать на уже стёртый url.

==================================================
17. PUBLISH
==================================================

Можно сохранить запись как draft: published = 0.
Черновик виден только в admin.

Publish ставит published = 1, запись появляется первой в публичной ленте, потому что createdAt свежий.

Unpublish прячет с публичной страницы, файлы не удаляет.

25. SECURITY
==================================================

Admin-эндпоинты только после requireCurrentAdmin().

Upload:
- whitelist MIME: image/jpeg, image/png, image/webp;
- расширение только из проверенного типа, не из имени пользователя;
- лимит размера (ориентир текущего проекта: 8 МБ на файл, можно поднять до 15 МБ для исходников арт-работ, но не выше без причины);
- имя файла — случайные байты, как в /api/upload;
- sharp читает файл; если sharp не смог декодировать картинку — отказ;
- svg, html, pdf, исполняемые и архивы отклонять.

Rich text:
- серверная санитизация перед записью в БД;
- повторно не доверять HTML из браузера;
- javascript: и data: в ссылках выкидывать.

Удаление: проверять, что media принадлежит entry, нельзя удалить чужой путь с диска по подсунутому url.
